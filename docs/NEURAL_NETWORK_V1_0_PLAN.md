# v1.0：Ti60 手势神经网络资源分析与实施规划

日期：2026-09-29。范围：仅本 CNN 副本，未合并主项目。

本版完成板卡/工程/参考资料核查、方案取舍、候选模型定义及可复现算量预算。**尚未训练手势模型，尚未接入 FPGA 推理，尚未生成神经网络位流。** 现有图像 RTL、工程 XML、原有 v0.x 注释均保持原状。

## 1. 建议路线与决策依据

建议首版采用“固定 ROI 静态手势 + 64×64 灰度 INT8 小型 CNN”，工程路线优先验证 **单核精简 Sapphire RISC-V + TFLite Micro + 按需 Lite 卷积加速**。先跑相同模型的纯软件基线，再通过逐层 profiling 决定是否启用加速、并行度取 1/2/4，以及普通卷积与深度可分离卷积的实际取舍。软件已经满足时延目标时可省去加速器。

这是依据现有条件提出的首选验证路线，不是已经证明全局最优。当前缺少目标手势数据、精度约束和上板时延，不能只凭参数量确定最终网络。暂按拳头、手掌、剪刀、无有效手势共四类预算；类别、ROI 范围和是否需要动态手势均可调整。任意位置识别还要增加手检测或候选区域搜索，动态手势还要增加时序样本和时序模型，不能用本次分类模型宣称已覆盖。

未来模型主要通过更新权重/软件并分时复用同一个推理引擎扩展，而不是为每个功能复制整套硬件。文字、面部、物品等任务是否能运行，仍要按具体网络的算子、内存和时延重新评估；预留资源不等于承诺这些任务都能同时实时运行。

## 2. 软核、硬核与 SoC 的关系

| 名称 | 在本工程中的含义 | 是否已存在 |
|---|---|---|
| Ti60 FPGA 硬资源 | XLR、DSP、片上 RAM、PLL、I/O 等芯片固定资源 | 存在，数量固定 |
| RISC-V | 指令集；Sapphire/VexRiscv 用 FPGA 逻辑实现 CPU，即软核 | 当前图像顶层未实例化 |
| Sapphire SoC | CPU、总线、缓存、启动存储器、外设组成的可配置软系统 | 在参考示例中，尚未接入当前工程 |
| TinyML | 小设备推理方法/平台，不是一颗处理器，也不是 Ti60 自带 NPU | 有参考软件和 RTL |
| TFLite Micro | 在 CPU 上调度量化神经网络算子的 C++ 运行库 | 参考示例随附版本 |
| TinyML 加速器 | 用 RTL 实现，消耗 XLR/RAM/DSP，经自定义指令及总线协作 | 参考示例，当前工程未实例化 |
| 专用 CNN 加速器 | 自写可复用 MAC 阵列、缓存、定点量化及控制器 | 备选路线，尚未实现 |

因此“TinyML / RISC-V / SoC”并非三个互斥方案。可组合为一个系统。Ti60 的硬 DSP 不等于现成神经网络处理器；本工程 DDR3 控制层同样包含软逻辑，不能照搬其它型号的硬 DDR 控制器假设。[Sapphire 官方说明](https://www.efinixinc.com/support/ip/riscv-sapphire.php)

## 3. 板卡事实及已有资源

本地 `Ti60_AR0135.xml` 指定 Titanium / Ti60F225 / C4，顶层为 `example_top`。本地数据手册第4页给出 60,800 XLR、256 个 10-Kbit RAM 块、160 DSP，F225 为4个 PLL。总片上 RAM 原始容量为 320 KiB；有效容量受端口宽度、深度、打包和独立缓冲限制。[官方 Ti60 数据手册](https://www.efinixinc.com/docs/titanium60-ds-v2.0.pdf)

`docs/sch/Ti60_F225_Core_V1.4.pdf` 第5页已做文本及图像核对：U2 是 MT41J128M16JT-125，x16 DDR3，128M×16 bit = 256 MiB；第7页为 W25Q64JWSSIQ，64 Mbit = 8 MiB SPI Flash。实物贴片、当前控制器地址范围、Flash 空闲布局仍需部署前确认。

**本板是该本地原理图所示的奥唯思核心板。** 官方 Ti60 F225 Development Kit 的256 Mbit HyperRAM是另一块板卡的配置，不能照搬该套件的引脚、存储控制器、时钟或演示 hex。[官方套件配置](https://www.efinixinc.com/products-devkits-titaniumti60f225.html)

| 资源 | Ti60 总量 | 图像工程历史 place 报告 | 算术剩余 | 本地独立 TinyML 示例历史报告 |
|---|---:|---:|---:|---:|
| XLR | 60,800 | 15,199（25.00%） | 45,601 | 44,027（72.41%） |
| 10-Kbit RAM 块 | 256 | 87（33.98%） | 169 | 145（56.64%） |
| DSP | 160 | 17（10.62%） | 143 | 47（29.37%） |

证据：`outflow/Ti60_AR0135.place.rpt`、`outflow/Ti60_AR0135.hier_util.rpt`；独立示例为 `tinyml-main/tinyml_hello_world/Ti60F225_tinyml_helloworld/outflow/...place.rpt`。图像工程 map 报告标注 Efinity 2026.1、2026-09-29，示例 map 报告为 Efinity 2025.1、2025-07-07。报告中的原始构建路径分别指向旧主目录和资料作者目录，**属于复制来的历史结果，未在本 CNN 副本重新综合**。audit 脚本保留报告 SHA256，防止后续误认为同一基线。

不能把两个整工程简单相加后当作接入资源；其中 DDR、时钟、总线等存在可复用或需重构部分。但简单相加的59,226 XLR、232 RAM已接近器件上限，足以否定“无需裁剪直接搬完整演示”的做法。官方旧 FAQ 的55,036 XLR/188 RAM等数字是另一版本/配置，不与本地报告混用。

现有层次报告中 DDR 控制器约4,938 XLR、30 RAM，说明复用它很有价值。历史时序报告最小受约束 setup 0.153 ns、hold 0.026 ns，余量较薄；加入总线和 CPU 后必须重新布局布线并检查全部约束/CDC。DSP宣传最高频率不能当作整个 CNN 系统工作频率。

### 建议资源门槛（设计目标，不是综合结果）

整工程先控制在 XLR ≤42,560（70%）、RAM ≤192（75%）、DSP ≤80（50%）。相对历史基线可新增上限为27,361 XLR、105 RAM、63 DSP；更理想的首版增量目标为20,000 XLR、64 RAM、32 DSP以内。布局布线余量和吞吐优先于把资源填满。达不到时先减少加速算子/缓存/并行度，再比较专用小型 CNN 引擎。

## 4. 已有数据链与接入边界

现有 AR0135 使用 DOUT[11:4] 的8位灰度采集，过滤前两行元数据及尾部统计行，再打包 RGB565；DDR 帧为1280×720×2字节。后续有几何变换、仓库回放/比较、可选中值/高斯/Sobel/Scharr/Canny以及 HDMI。RAW8 是总线取样方式；手势模型必须按实际显示/采集灰度分布训练，不能凭传感器名字假定获得 RGB 颜色。

推荐下一阶段的并联接入：

```text
AR0135有效图像灰度 ──┬── 已有RGB565 → DDR帧仓库 → 几何/ISP → HDMI
                    └── ROI裁剪/缩小 → 小图双缓冲 → CPU/TinyML → 类别/分数
                                                               └→ 状态/叠字
```

从过滤元数据后的8位灰度信号分支，保留训练和推理一致的预处理，避免用户切换 Canny、反相、缩放或回放时改变模型输入。当前 `ar0135_capture.v` 仅导出 RGB565；后续增加与 `pixel_valid` 同拍的灰度输出并标 v1.x，不能直接拼接原始 `cmos_data` 和延迟后的 valid。若改用 DDR 读帧，必须按实际 RGB565还原灰度的流程重新准备训练输入。

首版 ROI 可取中央512×512：在1280×720中左上角(384,104)，64×64每点对应8×8区域。优先评估整数区域平均以降低混叠；若为节省行缓存而用最近邻，训练、量化校准及板端必须全部采用同样采样坐标。下采样方法最终由实拍精度和资源决定，不能PC端双线性、板端抽点而不验证。

ROI 双缓冲用 FREE/WRITING/READY/READING 所有权，跨时钟用异步 FIFO 或稳定数据+握手邮箱；帧完成后才提交，CPU释放后才能覆盖。繁忙时丢弃整张新 ROI，不反压摄像头或HDMI。每个结果携带源帧号/时间戳，超时清空，不把旧结果长期叠加到新画面。

### DDR 与总线接入要求

- 已有 `axi4_ctrl` 的 `C_BUF_SIZE=22`，每槽地址跨度4 MiB；12槽预留48 MiB（0x00000000～0x02FFFFFF），有效图像数据每帧仅1,843,200字节。不要按有效像素大小紧接分配模型区，也不要复用被保存/显示占用的帧。
- 建议暂把0～64 MiB划为视频保留区，神经网络物理DDR区从0x04000000起规划。这里只是地址草案，CPU虚拟/总线地址可能有基址映射；必须与Sapphire内存图、链接脚本、控制器实际可寻址范围一起验证后落实。
- 复用唯一的 DDR PHY/控制器；在其前接多主 AXI 仲裁、必要的宽度/协议/时钟转换。现有用户总线为128 bit，不能直接将CPU或TinyML接到已被图像主机驱动的线上。
- 顶层现有视频控制端存在固定 `axi_bvalid=1`、`axi_bresp=0` 等专用约定。不能将这种应答复制给CPU/DMA；新增通用主机必须得到真实的事务完成/错误响应，并验证AW/W/B、AR/R和ID路由。
- 显示必须满足逐行供数期限，同时给推理有界的服务机会；使用受控突发/水位优先级和带宽计数器，禁止仅用可能饿死推理的永久最高优先级。验证突发4 KiB边界、背压、复位和错误恢复。
- CPU缓存与DMA/加速器共享缓冲要明确不可缓存映射，或执行提交前clean、读取前invalidate、内存屏障及所有权交接。仅把指针传给DMA不足以保证读到新帧。

若按60 fps估算，单路720p RGB565读或写约110.6 MB/s，读写合计221.2 MB/s，只是有效像素负载，不含突发损失、回放比较额外读数和推理。现有约74.4 MHz显示、74.25 MHz摄像头像素时钟不直接等于已经测得60 fps。ROI按64×64×1×15 fps仅约61.4 kB/s；优先小图分支可以避免为推理持续读取全帧。DDR标称速率不能代替实际持续带宽测试。

## 5. 方案比较

| 路线 | 优点 | 主要代价 | 本项目定位 |
|---|---|---|---|
| 精简RISC-V + TFLM纯软件 | 易验证、多算子可用、没有额外CNN硬件 | CPU逐层执行可能慢 | 同模型正确性/性能基线；满足目标则保留 |
| 精简RISC-V + TinyML Lite | 复用官方定点实现；可按需加速和换模型 | 仍要CPU、内存与CI接口；Lite也占资源 | 首选验证路线 |
| TinyML Standard / 完整EVSoC | 更高并行度、演示功能多 | 本地示例面积大、集成侵入性强 | 只在profiling证明需要时局部升级 |
| 自写可复用INT8 CNN RTL | 可针对小网络压低面积、确定性好 | 定点舍入/饱和/边界/访存验证工作大 | Lite路线不能兼顾资源和时延时备选 |
| PC完成推理、FPGA只采集 | 便于数据调试和建立参考结果 | 不满足板端独立推理 | 仅训练/验证工具链 |

Sapphire先选单核、关闭非必需FPU/MMU/外设，保留乘法支持、自定义指令接口、必要缓存和调试。**Sapphire Lite配置与TinyML Lite加速模式是不同概念**；必须核对选定Sapphire配置是否提供所需CI、AXI及BSP支持，不能因为两者都叫Lite就认为兼容。官方不同配置的Logic/Adders、FF表不能直接相加冒充XLR总量。

TinyML先仅启用Conv/Depthwise；FC仅192 MAC，先由CPU做。关闭未使用的Add/Mul/MinMax/LeakyReLU加速及不需要的通用演示DMA。Softmax可在输出后由软件按需计算。本地 `resource_lib.py` 的Lite卷积估计为DSP=`3+8P`，P=1/2/4对应11/19/35 DSP，**仅该子模块，不含CPU/共享模块/DDR**；RAM取决于生成器从模型推导的缓冲深度。不可用该公式当整机面积或用P直接推出端到端FPS。

## 6. 候选模型与明确的预算

v1.0新增 `ml/gesture/model.py`：提供候选结构、标准库预算CLI及延迟导入TensorFlow的 `build_model()`。当前没有训练权重。

推荐候选：Conv3×3/8/s2 → DW3×3/s2+PW1×1/16 → DW3×3/s2+PW1×1/32 → DW3×3/s2+PW1×1/48 → AveragePool → FC/K。卷积后ReLU，无残差，无LeakyReLU。64输入时空间尺寸64→32→16→8→4→1，四次降采样是否损伤细手指特征由实拍验证；96输入是备用。另有相同通道规模的普通卷积候选，防止Depthwise虽MAC少却因硬件利用率低反而较慢。

| 候选（K=4） | 卷积/FC MAC/次 | 训练参数含bias | INT8权重+INT32 bias字节 | 最大相邻输入输出张量字节 |
|---|---:|---:|---:|---:|
| 64灰度，深度可分离 | 196,288 | 3,108 | 3,600 | 12,288 |
| 96灰度，深度可分离 | 441,408 | 3,108 | 3,600 | 27,648 |
| 64灰度，普通卷积 | 884,928 | 19,956 | 20,280 | 12,288 |

MAC按一次乘加计1次，不含激活、池化、重定标、搬运和调度。权重字节不含FlatBuffer/量化尺度/对齐等；相邻张量字节也不是TFLM arena大小。实际arena包含临时scratch和持久元数据，应在所用TFLM版本通过RecordingMicroInterpreter/分配记录测峰值后定值。可先试64 KiB arena并保留扩展，绝不能把它视为已验证足够。[TFLM内存管理](https://github.com/tensorflow/tflite-micro/blob/main/tensorflow/lite/micro/docs/memory_management.md)

4类64模型若按96 MHz、1 MAC/cycle计算，理想计算下界约2.04 ms；这不是RISC-V指令执行速度或推理实测。建议首轮验收目标为10～15次分类/秒、端到端p95≤150 ms，曝光、取帧、预处理、排队、推理和去抖均计入；达不到时按profile优化，而不是先堆并行度。

### 提供模型资料的实际用途

`创建和导出模型/创建和导出模型/cretate_my_model.py` 没有 `fit()`，只有192×192×3、Conv32、LeakyReLU和随机初始化；输出192×192×32是特征图，不是手势类别。其单层约31,850,496 MAC，INT8输出约1,179,648字节，已超过整片原始RAM。权重文件小不代表推理内存小。

`convert.py` 用随机数做校准，适合演示导出API，不能证明真实手势量化精度。现有`.h5/.tflite`未独立反序列化核验，不推断它们一定与脚本完全一致，也不把它们称为可用的手势模型。保留参考文件不改动。

## 7. 训练、量化、部署的实施顺序

1. **定义类别和采集条件。** 确认首版静态手势、ROI距离、允许角度/光照/左右手。加入无手、其它手势、运动模糊和背景负样本。用AR0135实拍为核心，公共数据只做预训练补充。当前上位机没有已接通的HDMI采集适配器、串口图像读取已在v0.15删除，先落实可复现的图像采集途径。
2. **严格划分数据。** 按人员、采集会话/视频、场景分组，再划分train/validation/test，禁止相邻视频帧随机跨集合。起步可每类500～2000张有效且多样的ROI，但数量不是质量承诺。记录原帧/ROI/曝光/人员/会话及预处理版本。test不参与调参、阈值选择或量化校准。
3. **训练三个小模型对照。** 统一预处理与分组划分；输入灰度float32/255，输出logits，交叉熵使用from_logits=True。每类召回、macro-F1、混淆矩阵、无效手势误触发和不同人员表现均记录。64模型精度不足时先检查ROI和数据，再试96或增宽；不要直接换大检测网络。
4. **真实样本全整数量化。** 从训练集取100～500张覆盖类别/光照/背景的代表样本，设置INT8输入输出及TFLITE_BUILTINS_INT8。保存模型SHA、工具版本、labels、输入布局、scale/zero_point、每层算子及版本。量化公式为clip(round(real/scale)+zero_point)，不能默认将像素简单减128；需明确板端舍入规则。[官方整数量化流程](https://developers.google.com/edge/litert/conversion/tensorflow/quantization/post_training_integer_quant)
5. **量化回归。** 同一独立测试集比较float和INT8；目标建议macro-F1≥95%、每类召回≥90%、量化下降≤1个百分点，均为待确认验收目标。目标域连续无手视频验证误触发（建议≤1次/分钟）。输出logits不是概率，置信度阈值需基于validation做softmax或校准；未知输入需拒识与超时，不应必然映射为有效手势。
6. **先静态输入板端验证。** 用本地TinyML Generator分析新模型，生成配套 `defines.v`、`define.cc/.h` 和模型文件；只注册实际使用算子。PC TFLite、板端CPU参考、启用加速三者使用完全相同的INT8输入。原则上比对输出及可获取的中间张量；若官方加速核存在定点舍入差异，逐层定位并记录容差与分类影响，不能只看argmax相同。
7. **资源/时延扫描。** 同一模型比较软件、Lite P=1/2/4以及必要的局部Standard。记录每层时间、总p50/p95、arena峰值、DDR等待/峰值带宽、XLR/RAM/DSP、时序。兼容旧TFLM的转换工具版本必须以实际模型schema/op测试锁定；本地材料2024/2025、现有Efinity2026.1、上游工具不能盲目混用。
8. **接入实时ROI。** 完成双缓冲/CDC/总线仲裁/缓存维护后再接摄像头；测试ISP各模式、回放/对比、摄像头断开、DDR背压、异常复位。必须保持HDMI持续稳定，允许推理丢帧但不允许撕裂或用失效数据输出手势。
9. **结果稳定与扩展。** 用可调滞回/连续帧确认，结合结果年龄限制；去抖产生的延迟必须计入端到端指标。后续按同一引擎串行调度模型，只有确需并发实时才讨论额外硬件。
